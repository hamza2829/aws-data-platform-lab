# Failure drill and recovery

Run this only against a fresh LocalStack lab after `terraform apply`. The command
requires an empty curated watermark, so an existing run cannot be silently reset.
All six pipeline attempts and their S3 history records are generated by real code.
The CI integration repeats the drill and preserves the logs and reports as artifacts.

```bash
data-platform-lab failure-drill data/seattle-weather.csv --output runs/drill
```

The drill ingests seven daily raw objects, then injects a transform that deliberately
returns zero rows on 2012-01-03. The first two days reconcile and commit. On day three,
the candidate Parquet row count is zero while raw has one row; decimal sums also
disagree. The prepublication gate rejects it. No bad candidate is uploaded. The
watermark stays at 2012-01-02 and the run exits as failed.

Inspect `runs/drill/<run_id>/events.jsonl`, `reconciliation.json`, and
`reconciliation.md`. Filter JSON logs by the `run_id`. The failed day's stage is
`prepublication_reconciliation`; its reason contains `reconciliation mismatch` and
the raw and curated counts and sums. The last `watermark_committed` event identifies
2012-01-02; the `run_failed` event repeats the last good watermark. The Markdown report
shows exactly which partition and metrics disagree. Full evidence from the green CI
run is linked in the README.

The drill resumes without the injection. It processes 2012-01-03 through 2012-01-07
and leaves the first two days untouched. A subsequent incremental run processes no
days. Explicit reprocessing of 2012-01-01 replaces the same partition key and does
not rewind the watermark or add duplicates. Versioning retains the previous object.

The drill then renames `wind` to `gust` in a committed raw day and explicitly
reprocesses that day. Validation fails with `schema columns changed` before SQL or
publication. The report records `schema_validation`, the changed header, and the
unchanged watermark. Restoring the raw file and reprocessing the day succeeds.

To perform the first failure and retry manually in a fresh lab:

```bash
data-platform-lab ingest data/seattle-weather.csv
data-platform-lab run --inject-failure-day 2012-01-03 --output runs/manual
# Expected exit code 2. Inspect the printed run id and its report directory.
data-platform-lab run --output runs/manual
data-platform-lab run --day 2012-01-01 --output runs/manual
data-platform-lab history
```

The persistent state is `s3://aws-data-platform-lab-curated/_state/watermark.json`.
Each finished attempt writes `_history/<run_id>.json` and `_runs/<run_id>/` reports
and logs. Local copies remain under the requested output directory. Unit tests also
interrupt a state write after a valid partition is uploaded and corrupt a read-back
response. In both cases the watermark does not advance, and retry safely overwrites
the deterministic partition key.

This is a single-writer recovery protocol, not a multi-object S3 transaction. A process
kill can leave a valid published partition ahead of its watermark or only local/stdout
logs for the interrupted attempt. Retry reconciles and overwrites that day. Concurrent
writers, distributed locks, and transactional readers are outside this lab's scope.
